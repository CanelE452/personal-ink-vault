# 폴더 홈·통합 편집기·Rust 확대 설계안

2026-10-30. **사용자의 추가 질문 없는 구현 지시에 따라 개발 중이다. 전체 기능의 완료·새 배포를 뜻하지 않는다.** 사용자는 실제 역공학 조사 후 PPT·Obsidian식 지식 기능·문서 편집 등을 구현하도록 지시했고, StarNote 본체를 충분히 참조할 수 없으면 비슷한 다른 앱을 참고하는 것도 허용했다. Flutter 화면·필기 자산을 유지하고 Rust 공통 핵심을 연결하는 구성과 구현 순서는 이 지시에 따라 개발자가 선택했다. 기존 데이터와 이력은 보존한다.

현재 구현·검증 체크포인트는 [구현 계획](library-workspace-plan.md)에 기록한다. v2/폴더·Drive 형식 분리, 홈과 생성·저장 후 복귀, Rust FFI, 무한 필기·기기별 위치, 지식 패널과 탭/이력을 연결했다. PNG/PDF 썸네일 시험과 Android Office 포함 중간 앱 빌드도 통과했다. Windows 원본 편집 worker의 실제 왕복과 앱 UI를 별도 검사했고 현대 HWP/HWPX 엔진 연결은 진행 중이다. S9+ 실기기 수용·두 기기 Drive 왕복·최종 확대판 배포는 아직 통과하지 않았다.

## 사용자가 요청한 경험

앱을 열면 폴더와 문서 표지가 보이고, ‘생성’을 누르면 원하는 문서 종류를 고른다. 문서를 열어 필기하거나 편집한 뒤 뒤로가면 같은 폴더의 홈으로 돌아온다. StarNote의 폴더/표지/도구 접근 방식과 Obsidian의 Markdown·지식 연결을 한 작업 흐름으로 묶는다. 문서·PPT·한글은 PDF 필기 모드와 실제 원본 편집 모드를 구분한다. Android 휴대폰·태블릿과 Windows PC에서 이어 쓰며 Drive로 자동 동기화한다. Rust 사용 가능성도 검토한다.

구현은 홈·문서 탐색·뒤로가기·저장 경계를 먼저 연결하고 지식 기능·Rust 공통화와 Office 엔진 작업을 병행한다. Office 원본 편집과 현대 HWP/HWPX 요구를 PDF 변환만으로 대체하거나 완료 범위에서 빼지 않는다.

## 확대 요청 때 확인한 문제

아래는 확대 설계를 시작할 때의 결함 기록이다. 뒤로가기 수정은 preview.3에 반영됐으며, 새 홈·폴더·기기별 편집 제한 변경은 현재 통합 작업에서 다룬다. 과거 관찰을 최신 구현 상태와 혼동하지 않는다.

- [확인] 편집기의 뒤로가기 버튼은 옛 홈 경로로 이동하지만 현재 router가 다시 workspace로 돌려보낸다. 열린 문서는 route가 아닌 activeSession 상태이므로 닫히지 않는다. Android 시스템 뒤로가기에도 ‘저장 후 문서 닫기’ 계약이 없다.
- [확인] 문서 미선택 화면에는 안내문만 있고, 목록은 ListTile이다. 폴더·썸네일 홈·생성 타일이 구현되지 않았다. 현재 저장 모델도 제목/필기 ID/Markdown ID만 가진다.
- [확인] workspace의 저장 callback은 upstream 썸네일 생성 경로보다 먼저 반환한다. 표지 그리드만 배치해도 썸네일이 자동 생성되지는 않는다.
- [확인] 사용자 사진에는 생성된 노트 항목과 빈 페이지가 보인다. 이 사진만으로 PDF 원본이 손실됐다고 단정할 수 없다. PDF 가져오기·저장·재열기는 별도 수용 시험으로 확인한다.
- [확인] 현재 Android Markdown과 Windows 필기는 편집 역할을 제한했다. 확대안에서는 두 플랫폼 모두 편집 기능을 제공하고 화면 배치와 기본 선택만 기기에 맞춘다.

조사 대상: `lib/components/canvas/save_indicator.dart`, `lib/main.dart`, `lib/pages/workspace/`, `lib/data/vault/workspace_store.dart`, `lib/pages/editor/editor.dart`, `packages/ink_vault_core/`.

### 기존 분석의 범위와 누락

StarNote 조사는 APK의 매니페스트·archive·리소스와 공개 기능을 확인한 정적 조사다. 보호 래퍼 안의 본체 호출 흐름 복원이나 S9+에서의 실제 생성·편집·저장·복귀 관찰은 완료하지 않았다. Saber는 공개 소스의 재사용 검토와 이후 통합이며, Obsidian은 배포 코드의 일부 정적 경로 조사다. 이 결과를 세 앱의 실제 사용 흐름을 끝까지 역공학·검증한 근거로 삼을 수 없다. 특히 새 workspace와 기존 Saber 뒤로가기의 연결을 놓친 것은 우리 통합·검증의 누락이다.

새 화면은 사용자 제공 화면에서 확인되는 요구를 근거로 설계하고, 홈 → 생성 → 편집 → 저장 → 목록 복귀 → 같은 문서 재열기를 우리 앱에서 검사한다. APK 내부 단서와 UI 모양만으로 실제 파일 형식·상태 전환·필기 품질을 단정하지 않는다. 코드/호스트 시험 결과와 S9+ 실제 실행 결과를 별도로 기록한다.

후속 조사에서는 StarNote의 실제 JADX 래퍼·네이티브 경계와 번들 편집기 JavaScript를 분석했고 Obsidian 고정 ASAR의 함수 몸체와 호출 근거를 보강했다. StarNote 보호 본체의 홈·필기 런타임은 여전히 복원하지 못했다. 무한 문서·카메라·입력 상태는 [고정 Rnote 공개 소스 참조](rnote-source-reference.md)도 사용한다. Rnote 소스 읽기는 REA 배포 파일 분석이나 앱 실행 증거와 구분한다.

## 화면과 이동 계약

### 홈

- 태블릿·PC: 왼쪽에 전체 문서/최근 문서/폴더 트리/휴지통, 오른쪽에 현재 위치의 폴더와 문서 표지 그리드.
- 휴대폰: 같은 홈 그리드를 기본으로 두고 폴더 탐색은 접을 수 있는 메뉴로 제공.
- 상단: 현재 폴더 경로, 검색, 종류 필터, 정렬과 목록/그리드 전환. 문서 카드에는 제목·종류·수정 시각·동기화/충돌 상태를 표시한다. 내부 UUID는 일반 목록에서 숨긴다.
- 첫 ‘+ 생성’ 타일과 생성 버튼은 같은 메뉴를 연다. 생성한 문서는 선택한 폴더에 저장되고 홈에 카드로 나타난다.
- **빠른 메모**를 선택하거나 생성 타일을 두 번 탭하면 현재 폴더에 페이지 필기 노트를 한 개 만들고 바로 연다. 기본 제목은 `빠른 메모`다. 생성 타일을 한 번 탭하거나 키보드로 활성화하면 문서 종류 메뉴를 연다.
- 생성 메뉴의 목표 유형: 페이지 필기 노트, 무한 노트, Markdown, PDF 가져오기, 이미지/사진, Office·한글 가져오기, 새 폴더. 실제 제품 메뉴에는 해당 단계에서 생성·저장·재열기를 검증한 유형만 노출한다.

### 편집기

- 편집 화면은 문서에 집중하고 홈 서가로 돌아가는 명확한 뒤로가기 버튼을 둔다. 중복된 앱 제목 줄을 하나로 정리한다.
- 넓은 Android 화면에서는 문서를 여는 동안 서가를 접고 편집 영역 전체를 쓴다. 상단 화살표로 저장하고 현재 폴더로 돌아간다. Windows의 넓은 화면에는 폴더 서가와 필기·Markdown 배치를 함께 표시한다.
- 상단 도구줄에서 펜·형광펜·지우개·올가미·실행 취소/다시 실행·색·굵기·터치 이동을 바로 고른다. 도구 선택과 페이지/레이어 등의 부가 설정을 구분한다.
- PDF와 페이지 필기는 같은 필기 도구·선택·이동·저장 경험을 사용한다. PDF 원본과 필기는 별도로 보존한다.
- Android에서도 Markdown을 작성·미리보기할 수 있고 Windows에서도 지원 입력 장치로 필기할 수 있게 한다. 넓은 화면에서는 문서와 Markdown을 나란히 볼 수 있다.
- 문서 탭과 진짜 2차원 무한 캔버스는 별도 단계로 추가한다. 큰 유한 페이지나 연속 페이지를 무한 캔버스로 표시하지 않는다.

### 뒤로가기와 저장

화면 화살표와 Android 시스템 뒤로가기는 같은 workspace 동작을 사용한다. Drawer나 대화상자가 열렸으면 먼저 그것만 닫는다. 문서에서는 필기 저장 → Markdown 저장 → 진행 중 저장 완료 확인 → 편집 세션 닫기 → 원래 폴더·검색·스크롤 위치 복원 순서다. 저장 실패나 완료되지 않은 필기/가져오기가 있으면 작업본과 편집기를 유지하고 재시도/명시적 가져오기 취소를 제공한다. 홈에서의 시스템 뒤로가기는 OS의 기본 앱 종료/복귀 흐름을 따른다.

기존 Saber 경로는 workspace 전용 callback이 없을 때 기존 동작을 유지한다. 저장 상태 아이콘이 뒤로가기 기능을 대체하지 않도록 버튼 역할을 분리한다.

## 저장·폴더·썸네일

**문서 카드와 Markdown의 관계 — 작성자 기본안:** 기존 v1의 필기+Markdown 쌍은 같은 문서 카드 하나로 유지하고 두 내용 ID와 링크를 보존한다. 기존 정리 내용을 별도 카드로 자동 분리하지 않는다. 새 ‘Markdown 생성’은 독립 문서를 만들며 빈 필기 파일을 필수로 붙이지 않는다. 필기/PDF 문서에는 선택적으로 정리 Markdown을 연결할 수 있다. 독립 Markdown과 문서에 딸린 정리 영역은 화면과 문서 종류에서 구분한다.

1. 노트와 페이지 ID, 원본 PDF/첨부, 필기와 Markdown을 보존한다. 제목 변경·폴더 이동은 문서 링크의 식별자를 바꾸지 않는다.
2. 폴더에는 고정 ID, 부모 폴더 ID, 이름과 독립적인 변경/삭제 기록이 필요하다. 빈 폴더도 저장·동기화한다. **작성자 기본안:** 폴더 삭제는 관측한 하위 폴더·문서를 함께 휴지통으로 보내고, 같은 묶음으로 복원한다. 상위 폴더로 자동 이동시키거나 영구 삭제하지 않는다. 삭제와 동시에 다른 기기에서 수정·이동·새 자식 생성이 발생하면 이를 보존하고 충돌로 표시한다. 복원할 때 원래 부모가 없으면 홈의 미분류 위치로 돌린다. 삭제 시 관측한 자식과 부모 리비전을 기록해, 뒤늦게 도착한 작업을 조용히 삭제하지 않는다.
3. 썸네일은 `vaultId + noteId + inkRevisionId + rendererVersion`을 기준으로 기기에서 재생성하는 캐시다. 화면에 필요한 것부터 제한된 수로 생성한다. 캐시 실패나 삭제가 원본 저장·동기화에 영향을 주지 않아야 한다. 충돌 head의 표지는 구분한다.
4. v1은 새 필드를 이름 변경 때 지울 수 있고, 폴더 객체/새 kind를 읽지 못한다. 현재 저장소에 새 형식을 섞어 쓰지 않는다. 새 형식은 v1을 읽는 명시적 변환기와 구버전 쓰기 차단이 필요하다.
5. 안전한 이전의 기본안은 v1 원본·전체 백업을 유지하면서 별도 v2 저장소로 옮기는 방식이다. 기존 noteId/pageId와 현재 완전한 충돌 head를 모두 보존한다. 과거 이력은 v1 원본/아카이브에서도 계속 복구할 수 있어야 한다. 형식·Drive 폴더를 구분해 구버전 앱이 v2를 편집하지 못하게 한다. Drive 복사 용량과 중간 실패 후 재개를 측정한 뒤 전환한다.
6. 정확한 v2 직렬화와 이력 매핑은 호환성 시험을 포함한 구현 계획에서 확정한다. 변환 전후 ID·본문·첨부 해시·충돌/삭제 상태를 비교하는 gate를 통과하기 전에는 실제 사용자 저장소를 전환하지 않는다.

## Rust와 기기 지원

**구현 구성은 Flutter 화면·기존 필기 엔진과 Rust 공통 핵심이다.** 현재 연결은 JSON 요청을 받는 C ABI와 Dart FFI다. 지원 대상인 Android와 Windows에서 공통 핵심을 사용하며, S Pen 품질은 Galaxy Tab S9+ 실기기에서 별도로 검증한다.

- 첫 경계는 파일/해시 검증, 검색·역링크 인덱스, 폴더 연산처럼 입출력이 명확한 기능으로 잡는다. 초기 파일·리비전 발행자는 기존 Dart 한 곳으로 유지한다. Rust와 Dart가 같은 저장소를 동시에 쓰지 않는다.
- Rust와 Dart의 동일 입력 결과를 비교하고 Android/Windows 빌드·실행을 확인한 뒤 저장/동기화의 소유권을 모듈별로 옮긴다. 해시 함수 하나를 연결한 것을 전체 Rust 전환 완료로 표시하지 않는다.
- 펜 입력·화면 표시와 Google 계정 인증은 해당 플랫폼의 검증된 경로를 유지한다. 매 입력 획마다 불필요한 언어 경계를 왕복하지 않는다.
- 성능은 저장·검색·큰 PDF·필기 지연을 측정해 판단한다. Rust 도입만으로 더 빠르거나 파일이 작아진다고 보장하지 않는다.

대안은 Slint/Dioxus 등 Rust UI로 전면 재작성하는 방식이다. 플랫폼 지원 후보는 있으나 기존 Flutter 필기 엔진을 새 UI에 다시 연결하거나 재구현해야 하므로 현재 재사용 이점이 줄어든다. 또 다른 후보는 Office 앱과 연동하는 문서 허브다. 원본 편집은 빨리 활용할 수 있지만 ‘우리 앱 안의 직접 편집’과는 별도 기능이다. 현재 권고는 전면 재작성보다 혼합 구성으로 기존 데이터를 이어가는 것이다.

### 기업의 공개 구성 사례

사용자가 Rust 적용 기업의 구성을 추가로 질문했다. 아래는 각 공식 기술 글의 공개 시점을 기준으로 하며 현재 내부 구현 전체를 단정하는 자료는 아니다.

- [1Password 8 설계, 2021](https://1password.com/blog/1password-8-the-story-so-far): 통신·DB·암호화·권한·검색을 Rust 공통 코어에 모으고, iOS SwiftUI·Android 네이티브 UI·데스크톱 Electron을 연결했다. 이 앱의 공통 데이터 핵심과 화면을 분리하는 권고에 가장 가까운 사례다.
- [Dropbox Nucleus, 2020](https://dropbox.tech/infrastructure/rewriting-the-heart-of-our-sync-engine): 데스크톱 클라이언트의 동기화 엔진을 Rust로 재작성했다. 상태 모델과 재현 가능한 시험을 함께 설계했다. Dropbox의 전체 화면이나 모든 서버가 Rust라는 의미는 아니다.
- [Figma 구성, 2023](https://www.figma.com/blog/how-figma-draws-inspiration-from-the-gaming-world/): UI는 React/TypeScript, 캔버스는 C++/WebAssembly, 공동 편집 서버에는 Rust를 사용한다고 설명했다. UI·렌더링·동기화가 다른 기술을 쓰면서 하나의 제품으로 동작하는 사례다.
- [Zed](https://zed.dev/)와 [GPUI](https://gpui.rs/): 편집기와 GPU 기반 UI까지 Rust를 사용하는 사례다. 공식 Zed 배포 대상은 macOS/Linux/Windows다. 이 사례는 Rust UI 구현이 가능함을 보여주며, Android/iOS 필기와 S Pen 지원은 별도로 검증해야 한다.

이 사례에서 Flutter UI 채택 자체를 증명하는 것은 아니다. 공통 규칙과 화면의 책임을 분리하는 방식을 이 앱의 현재 자산에 적용하는 것이 작성자의 판단이다.

## Office·한글: 파일 열기, PDF 필기, 원본 편집

각 단계의 완료 기준을 구분한다.

- **가져오기/보관:** 원본 파일 바이트·종류·이름·리비전을 유지하며 홈과 Drive에서 관리한다.
- **PDF 필기 모드:** 지원 변환기로 만든 PDF를 기존 필기 편집기로 열고 다른 노트와 같은 도구를 사용한다. 변환 실패 시 원본은 유지한다.
- **원본 편집 모드:** PPTX의 텍스트 상자·도형·표·슬라이드 순서, DOCX의 문단·표·서식을 편집하고 다시 해당 형식으로 저장·재열기한다. 페이지를 이미지로 바꾸거나 파일을 외부 앱으로 여는 것과 구분한다. 구형 PPT/DOC와 HWP/HWPX는 각 엔진의 지원·변환 범위를 별도로 확인한다.

원본 문서 리비전, 해당 리비전에서 생성된 PDF, 그 PDF의 페이지에 연결된 필기를 따로 보관한다. 원본 편집으로 페이지·슬라이드 배치가 바뀌면 새 PDF를 만들고 기존 필기를 이전 PDF와 함께 유지한다. 동일 페이지 대응을 검증한 경우에만 필기 재연결을 적용한다. 두 기기에서 원본 편집과 필기가 동시에 일어나도 오래된 PDF에 대한 필기가 사라지지 않아야 한다.

공식 자료를 확인한 엔진 후보:

- ONLYOFFICE는 모바일 WebView에 편집기를 넣는 구조를 안내하며 문서/저장 서비스가 필요하다. 공식 모바일 웹 편집기는 상용 Enterprise/Developer 범위다. 따라서 서버·비용·통합 조건을 정해야 한다.
- ONLYOFFICE의 DOCX/PPTX 직접 편집 지원과 HWP/HWPX 보기·변환은 범위가 다르다. DOCX로 변환한 한글 문서를 원래 HWP 형식 그대로 왕복 편집한다고 표시하지 않는다.
- 한컴 SDK는 HWP/HWPX 처리·편집·PDF 변환을 안내한다. Android와 Windows 제공 범위와 계약 조건은 별도 조사 사항이다.
- Collabora의 모바일 오프라인 Office는 대안 조사 대상이다. 완성 앱이 있다는 사실만으로 우리 앱에 즉시 삽입할 수 있는 엔진이라고 판단하지 않는다.

초기 설계는 오프라인 필기·Markdown·기존 Drive 직접 연결을 유지한다. 서버형 Office를 채택할 경우 문서가 처리될 위치, 보관/삭제와 접근 권한을 별도 선택한 뒤 연결한다. 현재 문서를 새 서버로 전송하거나 유료 계약을 시작하지 않는다. 기존 GPL 기반 코드와 후보 엔진의 통합 조건도 채택 전에 확인한다.

## Obsidian에서 가져올 작업 방식

Markdown 원문·수식·검색·고정 문서/페이지 링크를 기본으로 유지한다. 다음에는 태그·문서 속성·일반 역링크·로컬 그래프와 문서를 배치하는 카드 캔버스를 추가한다. 필기의 무한 캔버스와 지식 연결용 카드 캔버스는 서로 다른 모델이다. Obsidian 플러그인 전체 호환과 StarNote 전용 원본의 완전 왕복 호환은 별도 검증이 필요한 추가 프로젝트다.

## 구현 묶음과 통과 조건 — 현재 구현 계획의 기준

**A. 사용할 수 있는 홈과 편집기:** 뒤로가기/저장/서가 복귀, 홈 그리드·생성 메뉴·표지, 기기별 도구줄, 폴더와 v1 이전/복원, 페이지 노트·PDF·Markdown 생성·재열기를 한 흐름으로 완성한다. A 내부에서는 기존 v1에서 navigation/홈을 먼저 검증하고, 폴더 형식 이전은 별도 gate로 검증한다. 화면만 달라진 것을 폴더 동기화 완료로 보지 않는다.

**B. Rust 공통화와 지식 기능:** Android/Windows에서 bridge를 검증하고 검증/검색/폴더 연산부터 단계적으로 이전한다. 뒤이어 태그·역링크·그래프·문서 탭과 진짜 무한 필기/카드 캔버스를 각각 구현·측정한다. 어떤 공통 모듈을 Rust가 실제 소유하는지 기록한다.

**C. 문서 원본 편집:** 합성 DOCX/PPTX/HWP/HWPX로 후보 엔진의 편집·저장·서식·오프라인/서버 조건을 비교한다. 선택한 엔진에서만 PDF/원본 편집 전환을 제공한다. HWP 원본 저장은 별도의 통과 조건이다. 변환 품질이나 통합 조건이 맞지 않으면 다른 엔진을 계속 검토한다. 외부 Office 앱 열기나 PDF 변환만으로 우리 앱의 원본 편집 요구를 완료한 것으로 표시하지 않는다.

필수 수용 시험:

1. 화면/시스템 뒤로가기, Drawer 우선 닫기, 미저장 필기·Markdown·PDF 가져오기·저장 실패 중 작업본 보존.
2. 생성 → 홈 카드 → 재시작 후 재열기. PDF 배경·획·원본 자산 바이트 보존. 가로/세로·휴대폰/태블릿/Windows 화면 확인.
3. 폴더 생성/이름 변경/이동/삭제 복원과 오프라인 충돌, 기존 문서·페이지 링크 유지, v1→v2 변환 중단/재개/백업 복원.
4. 썸네일 캐시 삭제·실패·오래된 리비전에서도 원본 저장과 Drive 동기화 유지.
5. Rust/Dart 호환 벡터, Android/Windows 실제 빌드, 파일 접근·리소스 정리, 기존 회귀시험과 새 홈·지식·무한 필기·Office 시험. 이전 배포판의 전체 시험 결과를 새 변경의 최종 결과로 재사용하지 않는다.
6. S9+→Windows 필기/Markdown/폴더 왕복과 동시 수정·백그라운드 재시작. 기존 앱의 ‘Drive 반영 완료’ 화면만으로 PC 수신 성공을 판단하지 않는다.
7. Office 원본 객체 편집 → 해당 형식 저장 → 다른 편집기 재열기; 새 PDF 생성 후 기존 필기 보존. 표·수식·글꼴·슬라이드 배치가 깨지는 표본은 손실 범위를 기록한다.

같은 핵심 문제가 원인별 수정·실기기 재검증을 두 차례 거쳐도 남으면 필기 엔진 재사용/대체를 다시 비교한다. Office 후보는 원본 보존이나 필수 왕복 편집을 통과하지 못하면 채택하지 않는다. 구체적인 SDK 버전, 캐시 크기, 작업 병렬도와 UI 세부 간격은 구현자가 실측 후 결정한다.

## 구현자가 선택한 구성과 남은 외부 조건

- Rust 범위는 Flutter 화면 + Rust C ABI 공통 핵심으로 구현 중이다. 검색·링크·검증·폴더 연산부터 연결하고, 저장/동기화 writer 전체의 Rust 이전은 아직 완료하지 않았다.
- A의 탐색·저장 경계를 우선 연결하면서 B·C를 병행한다. Office 원본 편집·현대 HWP/HWPX도 전체 목표에 남긴다. 통상 구현 선택을 위한 추가 사용자 답변은 기다리지 않는다.
- 상용 SDK/새 문서 처리 서버는 선택하지 않았다. 현재 구현 지시는 유료 계약이나 개인 문서를 새 서버에 전송하는 승인을 포함하지 않는다.

## 데이터베이스 공통 계산 계약

후속 구현의 `workspace_query`는 수식·관계·롤업과 필터·정렬·그룹·집계·달력·차트를 Rust에서 계산한다. 호출자가 고정한 본문과 관련 DB, UTC 시각을 한 번에 전달하고 순서 있는 연산 묶음에서 계산 한도·캐시·오류를 공유한다. 계산값은 파생 결과이며 원시 DB 본문이나 행의 페이지 본문에 저장하지 않는다. 기존 저장·Drive writer를 함께 이전했다고 해석하지 않는다.

문자열과 객체 키는 `utf16-v1` 평면 노드로 전달해 단독 surrogate와 원본 키 순서도 보존한다. 노드는 자식 뒤에 배치하고 중복 참조·순환·중복 키를 거부한다. 깊이128, 노드200,000, 키·문자열 합계 UTF-16 단위2,000,000, 요청32MiB·응답8MiB, 연산512개·셀10,000개를 상한으로 사용한다. 한도를 넘으면 명시적으로 실패하며 결과를 잘라 성공으로 표시하지 않는다. 값별 계산 깊이와 전체 계산 budget은 별도로 적용한다.

Flutter 편집기는 원시 셀을 계속 편집·저장하고 계산 결과만 공통 엔진에서 받는다. 엔진 실패 시 계산 오류를 표시하며 Dart로 몰래 다시 계산하지 않는다. Dart 구현은 호환 벡터의 기준과 엔진이 주입되지 않는 기존 시험 경로에 남는다. 큰 정수 반올림의 중간 정수 곱셈, 잘못된 Unicode escape, 같은 날짜의 달력 순서처럼 기존 기준에서 발견한 결함은 회귀 시험과 함께 명시적으로 수정한다.

MCP의 계산 조회도 같은 Rust runtime과 저장된 본문 판본을 사용하도록 연결한다. 미저장 편집 내용을 저장하거나 외부 입력 DB를 실행하는 조회가 아니다. 실제 DLL 대조·앱 통합·두 플랫폼 빌드 결과는 [검증 기록](mvp-validation.md)에 별도로 남기며 계약 설계만으로 실행 완료를 주장하지 않는다.

## 카드 캔버스의 공개 형식 참조

2026-10-30 공식 [JSON Canvas 1.0 명세](https://jsoncanvas.org/spec/1.0/)(2024-03-11)를 직접 확인했다. 노드·연결선 배열의 순서, 텍스트/파일 카드, 위치·크기·색·연결 필드를 참조한다. 새 카드 캔버스는 읽은 JSON의 알 수 없는 root/node/edge 필드를 유지하며, 외부 HTML이나 URL을 실행하지 않는다. 앱에서 만든 file 카드 값은 현재 저장소의 note ID에 대조해 문서 열기 callback으로만 해석한다. 임의 파일 경로를 열지 않으며, 외부 Obsidian vault의 파일 경로까지 자동 연결된다는 뜻은 아니다. 화면 위치와 배율은 본문 JSON·Drive와 분리된 기기별 상태다.

이 항목은 공개 데이터 형식 참조다. 앞선 Obsidian 배포 ASAR의 REA 조사, 실제 앱 실행, 전체 플러그인 호환성 검증과 구분한다. 제품 코드·자산은 복사하지 않았다.
